Lua for Configs Lesson 01

Values, local & truthiness

Four surprises Lua has waiting for a Python/Ruby brain — and every one of them shows up in the first ten lines of a real config.

You already know how to program. So we start not with "what is a variable," but with the handful of things Lua does differently from Python and Ruby. Get these four wrong and a config line does something quietly other than what you read. Get them right and you can already read most of the ifs, defaults, and assignments in any init.lua or hyprland.lua.

1 · A bare variable is global

In Python and Ruby, a plain assignment inside a scope makes a local. In Lua it's the opposite: a bare name is a global. You opt into locality with the local keyword.

x = 10          -- GLOBAL. Visible everywhere, forever.
local y = 10    -- local to this chunk/block. What you almost always want.
This is the one place shell is your anchor, not Python: a plain FOO=1 in a shell script is global too, and you reach for local inside a function to contain it. Lua works the same way — except you want local almost everywhere, not just in functions.
Forgetting local doesn't error — it silently creates a global. In a config that require()s several files, a stray global in one file can clobber a name in another. Rule of thumb: type local until you have a specific reason not to.

At the top level of a Neovim init.lua, the line greeting = "hi" does what?

Global. No local keyword means the name is written into the global environment table (_G). Harmless here, but a habit worth breaking early.

2 · Only nil and false are falsy

This is the big one. In Lua, every value is truthy except nil and false. That means 0, 0.0, the empty string "", and the empty table {} are all truthy.

Lua's rule is exactly Ruby's rule. If you think in Ruby here, you will never be wrong: only nil and false are falsy in both. It is Python that misleads you — Python treats 0, "" and [] as falsy, and Lua does not. When your Python instinct fires here, override it with Ruby. 
if gaps == 0 then ... end   -- correct: test the value explicitly
if gaps then ... end         -- gaps == 0 still enters here! 0 is truthy.

Which one of these is falsy in Lua?

nil is falsy; the other three are all truthy. If you pictured Python's rules you'd have flagged zero and the empty string too — that's the trap.

3 · nil means "absent", and reading it is not an error

nil is Lua's None/nil: the absence of a value. The Lua-specific part is how forgiving reads are. Referencing a variable that was never set, or a table key that isn't there, returns nil — it does not raise.

local cfg = { width = 80 }
print(cfg.height)   --> nil   (no KeyError, no NameError)
print(undefined)    --> nil   (unknown global, still just nil)
Closer to Ruby's hash[:missing] → nil than to Python's KeyError. The upside: presence checks are just if cfg.height then. The downside is the gotcha below.
Because a typo'd key silently reads as nil instead of crashing, a misspelled option in a config often fails silently — the setting simply never takes effect. When a config line "does nothing," suspect a nil from a typo first.

4 · The default idiom, and three syntax tells

Surprises 2 and 3 combine into the single most common idiom you'll see in configs — the or default, identical to Ruby's x ||= default:

local width = opts.width or 80   -- if opts.width is nil/false, use 80

Predict the two printed lines, then reveal.

local width = nil
local w = width or 80
print(w)
print(0 and "reached")

80 then reached.

width is nil (falsy), so or returns its second operand, 80. In the second line 0 is truthy, so and evaluates and returns its right-hand side, the string "reached". A Python instinct would expect the 0 to short-circuit — it doesn't.

Nothing in this lesson diverges between Neovim 5.1 and Hyprland 5.4: local, nil, and truthiness are identical in every Lua version. The first real divergence — how numbers behave — is next lesson.
