Lua for Configs Lesson 04

Control flow & iteration

The ifs and loops are the easy part — the traps are the exact keywords, an inclusive for range, and the fact that pairs hands you keys in no particular order.

You know branching and looping cold in three languages. So this lesson is only about where Lua's spelling and semantics differ — the keywords it insists on, the one range convention that counts differently from Python, and the two table-walking functions you'll use in every config. Truthiness (Lesson 01) and tables (Lesson 03) are the ground this stands on.

if wants then and end

No colons, no braces, no significant indentation. A conditional opens with then and the whole thing closes with end. "Else if" is the single word elseif.

if opts.wrap then
  mode = "soft"
elseif opts.width > 100 then
  mode = "wide"
else
  mode = "default"
end
Four keyword tells against what you already type: it's elseif (one word), not Python's elif, Ruby's elsif, or JS's else if. It's ~= for "not equal" (Lesson 01), never !=. The condition needs no parentheses. And indentation is cosmetic — only then/end delimit the block. The condition follows Lua truthiness: only nil/false skip the branch, so if opts.width then runs even when width is 0.

There is no ternary — and/or stands in

Lua has no a ? b : c. The idiom is cond and a or b, leaning on the short-circuit return values from Lesson 01. It's the same trick as Python's old a if cond else b workaround.

local width = opts.wide and 120 or 80   -- wide? 120 : 80
The idiom silently breaks when the "true" branch is itself falsy. In local x = flag and false or true, when flag is truthy you still get true — because and yielded false, so or moved on to its right side. Only use cond and a or b when a can never be nil/false. When it can, write a real if.

The numeric for counts inclusively

for i = start, stop do … end runs with i taking every value from start to stop — including stop. An optional third number is the step.

for i = 1, 3 do io.write(i) end      --> 123   (1, 2, AND 3)
for i = 10, 1, -1 do … end       -- countdown with a step of -1
This is the opposite convention to Python's range(1, 3), which stops before 3, and unlike a C/JS for (i = 1; i < 3; i++) with its <. The upside: because tables are 1-based (Lesson 03), for i = 1, #t do walks exactly keys 1 through #t with no off-by-one — start and end both line up with the table.
In Lua 5.4, when start, stop, and the step are all integers the loop variable is an integer — so for i = 1, #t gives integer indices (#t is an integer), ideal for array work. Make any bound a float and the variable turns float: for i = 1.0, 3 yields 1.0 2.0 3.0. In Lua 5.1 there are no subtypes, so i is always a float and just prints as 1 2 3. Practical rule: keep loop bounds integer literals (or #t) when the counter is a table index. (5.4 also computes the iteration count up front, dodging the counter-overflow infinite loop that huge bounds can cause on 5.1 — rarely relevant at config scale.)

How many times does the body of for i = 1, 3 do … end run?

Lua's numeric for includes the end value, so i is 1, 2, 3 — three iterations. Python's range(1, 3) stops before 3; Lua does not. The step defaults to 1 when omitted.

pairs vs ipairs — walking a table

The generic for … in drives an iterator. Two come built in, and choosing wrong is a classic config bug.

-- ipairs: the ARRAY part only, keys 1,2,3… IN ORDER, STOPS at the first nil
for i, v in ipairs(list) do print(i, v) end

-- pairs: EVERY key (array + hash), order UNSPECIFIED
for k, v in pairs(opts) do print(k, v) end
pairs gives no order guarantee — not insertion order, not sorted order. This bites Python and Ruby brains hard: both languages iterate hashes in insertion order, so code that "just happened to come out in order" there will come out scrambled here, and can differ run to run. If you need a stable order, collect the keys into a sequence and table.sort them, or use ipairs over an explicit array. Also recall Lesson 03: ipairs stops at the first nil, so a hole hides every later element from it.

What can you rely on about the order in which pairs(t) yields keys?

The Lua manual specifies no order for pairs, and it can even vary between runs. Unlike Python 3 dicts and Ruby hashes (both insertion-ordered), you must sort keys yourself or iterate an explicit sequence when order matters.

while and repeat

Two more loops, rarely needed in configs but worth recognising. while tests first; repeat … until tests after the body (so it always runs at least once) and — unusually — its condition can see locals declared inside the body.

while queue.pending do step() end

repeat
  local line = read()
until line == nil          -- note: the UNTIL is the EXIT test, and sees `line`
repeat … until cond is a do-while, but watch the sense: the condition is when to stop, the mirror image of while's "keep going while true." Ruby's begin … end until is the same idea; Python has no direct equivalent.

Predict the printed number, then reveal.

local t = { "a", "b", nil, "d" }
local n = 0
for _ in ipairs(t) do n = n + 1 end
print(n)

2. ipairs walks 1, 2, then hits the nil at key 3 and stops — "d" at key 4 is never seen. This holds on both 5.1 and 5.4.

Contrast: pairs(t) would visit "d" (it walks all real keys, including 4), just in no guaranteed order. That gap between the two iterators is exactly the hole trap from Lesson 03.

Putting it together

The two iterators against the nested config from Lesson 03 — ipairs for the list of keymaps, pairs for the option hash:

for _, map in ipairs(config.keymaps) do
  print(map[1], map[2], map[3])   -- each map is a 3-item array
end

for key, value in pairs(config.colors) do
  print(key, value)                -- fg/bg, in SOME order
end
Primary: Lua 5.4 Reference Manual §3.3.5 "For Statement" for the numeric/generic for and its integer rules, and §6.1 on next/pairs for why pairs has no defined order.
