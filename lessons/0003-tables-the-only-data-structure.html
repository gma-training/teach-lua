Lua for Configs Lesson 03

Tables: the only data structure

Lua has exactly one container, and a config file is nothing but that container nested inside itself. Learn the table and you can read the shape of any config.

Lua gives you one compound type: the table. It does the job that Python splits across dict, list, and object, and that Ruby splits across Hash and Array. Everything structured in a config — options, nested groups, lists of keymaps — is a table. There is no separate list type to learn. Master the four things below and the wall of braces in any init.lua or hyprland.lua resolves into a shape you can read.

One constructor, two shapes

The braces { } build every table. Give it positional values and you get an array-like part (keys 1, 2, 3…); give it key = value pairs and you get a hash-like part. You can mix both in one literal.

local list = { 10, 20, 30 }            -- array part: keys 1, 2, 3
local opts = { width = 80, wrap = true }   -- hash part: string keys
local mix  = { "a", "b", tag = "x" }      -- both at once
Think Python's dict and list fused into one thing. The closest single-structure cousin is the JavaScript object: { width: 80 } in JS maps almost 1:1 onto Lua's hash part. The difference: JS keeps a separate Array, whereas Lua folds the array into the same table as integer keys.
Tables are 1-based. The first array element is t[1], not t[0]. Every other language you know — Python, JS, Ruby — counts from 0. In Lua the sequence { 10, 20, 30 } occupies keys 1, 2, 3. t[0] is just an ordinary key that nobody set, so it reads as nil.

For local t = { 10, 20, 30 }, what does t[0] evaluate to?

The literal filled keys 1, 2, 3. Key 0 was never assigned, and reading a missing key is never an error in Lua — it just returns nil (Lesson 01). The first element lives at t[1].

Two ways to write a key — and they're identical

For a string key that looks like an identifier, t.width is pure sugar for t["width"]. They compile to the same access. But a key that isn't identifier-shaped — a hyphen, a leading digit, a number, a boolean — can only be reached with brackets.

opts.width          -- sugar
opts["width"]       -- exactly the same access
opts["line-count"]  -- MUST use brackets (hyphen isn't an identifier)
list[1]            -- numeric keys are always brackets
This dot-vs-bracket duality is JavaScript, not Python/Ruby. JS has exactly the same obj.width / obj["width"] pair and the same "use brackets for obj["max-width"]" rule. Python (d["width"]) and Ruby (h[:width]) only offer the bracket form for their hashes. If you already reach for brackets-on-weird-keys in JS, that instinct is correct here.

Missing key is nil; assigning nil deletes

Reading a key that was never set returns nil — the same forgiving read from Lesson 01, now on tables. The flip side is the surprise: writing nil into a key doesn't store nil, it removes the key.

local cfg = { width = 80 }
print(cfg.height)   --> nil   (no KeyError, no undefined-is-a-value quirk)
cfg.width = nil     -- the key "width" is now GONE, not set to nil
The read side matches JavaScript closely: obj.missing gives undefined rather than throwing, just as Lua gives nil. The mental difference: JS actually stores undefined/null as values, whereas in Lua "the key holds nil" and "the key does not exist" are the same state — which is why assigning nil deletes.

Length with #, and the hole trap

The # operator gives the length of the array part of a table. On a dense sequence (keys 1..n with no gaps) it's exactly what you expect.

local t = { 10, 20, 30 }
print(#t)   --> 3

But punch a nil hole in the middle and # is no longer trustworthy — it may return any border of the gap.

t[2] = nil       -- now the sequence has a hole at key 2
print(#t)     -- may print 3, or 1 — it is UNDEFINED
The result of # on a table with holes is unspecified in both Lua 5.1 and Lua 5.4 — the manual only promises a meaningful length for a border-free sequence. The two versions use different internal length algorithms, so the same holey table can genuinely report a different # under each. Rule: keep sequences dense (no nil in the middle), and when you need to drop an item, rebuild the list rather than nil-ing a slot. Note too that ipairs stops at the first nil, so it and # agree on clean sequences and both mislead on holey ones.

After local t = {10,20,30}; t[2] = nil, what may #t return?

A nil in the middle makes this a non-sequence, and # on a non-sequence is unspecified — it may report either border of the hole, and 5.1 and 5.4 can differ. Never rely on # once a table has holes.

Unpacking a table — the second divergence

Spreading a sequence into separate values (for a call, or multiple assignment) uses a function whose name moved between versions.

local rgb = { 255, 128, 0 }
-- Lua 5.1:  unpack(rgb)          (a global)
-- Lua 5.4:  table.unpack(rgb)    (moved into the table library in 5.2)
Lua 5.1 exposes a global unpack. Lua 5.4 removed that global and provides table.unpack instead. Calling table.unpack on 5.1 errors (no such field); calling bare unpack on 5.4 errors (it's a nil global). The portable line that runs on both: local unpack = table.unpack or unpack, then call unpack(rgb).

Predict all three printed lines, then reveal.

local m = { "red", "green", tag = "warn" }
print(#m)
print(m.tag)
print(m[3])

#m → 2. Only "red" and "green" occupy the array part (keys 1 and 2); tag is a string key and lives in the hash part, which # ignores.

m.tag → warn. The dotted access reads the string key.

m[3] → nil. Nothing was assigned to numeric key 3; tag = "warn" set the key "tag", not 3.

Tables are references

A table value is a reference. Assigning it to another name doesn't copy — both names point at the one table. And == compares identity, not contents.

local a = { 1, 2 }
local b = a
b[1] = 99
print(a[1])        --> 99   (a and b are the same table)
print({1} == {1})  --> false (two different tables, same contents)
No surprise here — this is exactly Python's list/dict aliasing (b = a then mutate), Ruby's object references, and JavaScript's objects/arrays. Your instinct from all three transfers unchanged: to actually copy a table you must build a new one and copy the entries in.

Putting it together: a config is nested tables

That's the whole point. Every config you'll read is one outer table whose values are more tables, freely mixing the array and hash shapes:

local config = {
  width = 80,
  wrap  = true,
  keymaps = {                       -- an array of arrays
    { "n", "<leader>w", "save" },
    { "n", "<leader>q", "quit" },
  },
  colors = { fg = "#eee", bg = "#111" },  -- a hash
}

print(config.keymaps[1][2])   --> <leader>w
print(config.colors.bg)        --> #111

Read that chain left to right: config is a table, .keymaps is the array inside it, [1] is its first entry (another array), [2] is that array's second slot. No new syntax — just the four rules above, nested. This is config-scale Lua in full.
